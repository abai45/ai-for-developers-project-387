# Решения по контракту

Документ фиксирует архитектурные решения проекта «Календарь звонков» на этапе проектирования.
Используется как источник истины при написании TypeSpec-контракта и реализации.

## Docker и деплой (тикет #19/#20, финальный блок курса)

- **Один образ, один порт** — фронтенд собирается Vite (`dist/`) и укладывается в `backend/src/main/resources/static`, Spring Boot отдаёт его как статику; API (`/api/**`) и UI живут на одном порту. Отдельный nginx/прокси не нужен, CORS не нужен (тот же origin)
- **Dockerfile в корне, мультитейдж** — `node:22-alpine` (сборка фронта, `npm ci`) → `maven:3.9-eclipse-temurin-21` (копирует `docs/openapi.json`, `frontend/dist` → static, `mvn package -DskipTests`; серверные артефакты openapi-generator генерируются на сборке как обычно) → `eclipse-temurin:21-jre` (Entrypoint `java -jar`); в `.dockerignore` — node_modules, target, dist, .git
- **Порт из окружения** — `server.port=${PORT:8080}` в `application.properties`; хостинг (Render/Railway) и локальная проверка задают `PORT`
- **SPA-fallback** — ресурсный резолвер отдаёт существующий файл из `static/`, иначе (кроме `api/…`) `index.html`, чтобы маршруты React (`/owner`, `/book`, `/book/success`) открывались прямым заходом; контроллеры `/api` имеют приоритет над ресурсным обработчиком
- **MCP-конфигурация** — в `opencode.json` локальный MCP-сервер хостинга с ключом из переменной окружения (`{env:RENDER_API_KEY}`), сам ключ в git не попадает; инструкция подключения — в README
- **Данные** — хранилище остаётся in-memory: перезапуск/редеплой контейнера сбрасывает типы и встречи (зафиксировано в README)

## Параметры расписания

| Параметр | Значение |
|---|---|
| Часовой пояс владельца | `Asia/Almaty` (UTC+5, без перехода на летнее время) |
| Часы работы владельца | `09:30` – `18:00` |
| Окно записи | ровно **14 календарных дней**: со следующего дня включительно, последний день — «завтра + 13»; интервал `[сегодня+1д 00:00, сегодня+15д 00:00)` |
| Длительность слота | равна `durationMinutes` выбранного типа встречи |
| Шаг старта слотов | задаётся для каждого типа отдельно — `slotStepMinutes` |
| Пересечение интервалов | запрещено, включая частичное наложение, **между типами в том числе** |
| Касание интервалов | разрешено: новая встреча может начинаться в момент окончания предыдущей |
| Одновременные запросы | проверка на пересечение и создание брони выполняются атомарно |
| Гость | вводит имя (`guestName`, обязательное поле) и необязательную тему разговора (`topic`, до 100 символов; пустая/пробельная нормализуется к отсутствию) |
| Владелец | один, задан в приложении константой; авторизации нет |

### Правила расчёта слотов

- Свободные старты для типа: `09:30 + k × slotStepMinutes`, пока `старт + durationMinutes ≤ 18:00`.
- Слот считается свободным, если его интервал `[старт, старт + длительность)` не пересекается ни с одной существующей бронью любого типа.
- Пример шага: «Короткий созвон» 15/15 → старты 09:30, 09:45, …; «Воркшоп» 60/60 → 09:30, 10:30, ….

### Валидация типа встречи

- `name` — 1–100 символов (непустая строка)
- `description` — до 500 символов, может быть пустым
- `durationMinutes` — от 1 до 510 (= длина рабочего дня 09:30–18:00)
- `slotStepMinutes` — от 1 до `durationMinutes`

## Решения по API (интервью 26.10.2026)

- **Время в API** — ISO-8601 с явным смещением владельца: `2026-10-27T09:30:00+05:00`
- **Слоты для гостя** — эндпоинт возвращает **все** слоты окна со статусом `free` / `occupied` (без данных гостя); при бронировании перепроверка на сервере → `409`
- **Список встреч владельца** — только предстоящие (`start ≥ сейчас`), по возрастанию
- **Скоуп операций** — только: создать тип, список типов, слоты, забронировать, предстоящие встречи. Отмена брони и редактирование/удаление типов — **вне скоупа**
- **Ошибки** — RFC 9457 `application/problem+json`
- **Успешное бронирование** — `201 Created` + полное тело встречи
- **«Подключиться ко встрече»** = записаться на свободный слот; отдельного экрана входа в встречу нет

## Роли (корректировка 26.10.2026)

В проекте две условные роли, авторизации нет:

- **Владелец** — один заранее заданный профиль, используется в админской части; создаёт типы событий и видит страницу предстоящих встреч (все типы одним списком)
- **Гость** — бронирует слоты без аккаунта и входа; видит список типов событий (название, описание, длительность), выбирает тип, затем свободный слот на 14 дней и создаёт бронирование

**Доступ владельца** — карточка «Создать встречу» гостям не показывается; владелец заходит по прямой ссылке `/owner`, в футере — тонкая ссылка «Владелец».

## Общие секции screens.md (вопрос карты #5, 31.10.2026)

- **Состояния** — своя четвёрка `loading / empty / error / ok` у **каждой секции экрана** (не страницы целиком): `loading` → скелетон (shadcn `Skeleton`); `empty` → заголовок + пояснение; `error` → «Не удалось загрузить данные» + кнопка «Повторить»; `ok` → контент
- **Канонические тексты** — «Загрузка…»; «Пока ничего нет» / предметно «Типов встреч пока нет», «Свободных слотов на этот день нет»; «Не удалось загрузить данные» + «Повторить»; `409` → «Слот только что заняли, выберите другой» + автоперезагрузка слотов; экраны уточняют только предметные вставки
- **Ошибки API** — `application/problem+json` (RFC 9457): `type: about:blank`, `title`, `status`, `detail` на русском; для `400` — массив `errors: [{ field, message }]` для подсветки полей формы; `404`/`409` — одним `detail`
- **Показ ошибок** — встроенное состояние `error` в упавшей секции, без глобального оверлея; секции независимы; `409` в мастере — сообщение у списка слотов, мастер не закрывается
- **Адаптивность** — mobile-first, единственный перелом `md` (768px): `/book` на десктопе три колонки по референсу, на мобилке вертикальная последовательность; `/owner` на мобилке один столбец, на десктопе «форма + списки»
- **Доступность** — видимый фокус (shadcn по умолчанию), один `h1` на экран без прыжков уровней, `alt` у содержательных картинок, `label` у всех полей, ошибки с `role="alert"` / `aria-live`
- **Компоненты** — база shadcn: `Skeleton`, `Button`, `Card`, `Label`, `Input`, `Textarea`, `Sonner`; кастом — только сетка месяца по референсу (поправка вопроса карты #3: добавлены `Textarea` и `Sonner` — тост только для submit-исходов форм; `Alert` исключён)
- **Секции `screens.md`** — порядок: Общие правила → Лендинг `/` → Владелец `/owner` (#3) → Гость `/book` с экраном «Вы записаны» (#4)

## Контракт: структура и форма TypeSpec (вопрос карты #2, 31.10.2026)

- **Где живёт контракт** — исходники TypeSpec в `docs/spec/tsp/`: `main.tsp` (импорты, `@service`), `models.tsp`, `routes.tsp`, `errors.tsp`, `package.json` + lockfile (пины `@typespec/compiler`, `@typespec/openapi3`), `tspconfig.yaml`; генерат — `docs/openapi.json` (коммитится, дрейф-чек в `mise run check`)
- **Метаданные сервиса** — `@service({ title: "Календарь звонков API", version: "1.0.0" })`, OpenAPI 3.1
- **Операции** — `createEventType`, `listEventTypes`, `listSlots`, `createMeeting`, `listMeetings`, `healthCheck`; пути: `POST /api/event-types`, `GET /api/event-types`, `GET /api/event-types/{eventTypeId}/slots`, `POST /api/meetings`, `GET /api/meetings`, `GET /api/health`; query-параметров нет (окно и рабочее время зафиксированы на сервере); `health` отвечает `200` без тела
- **Нейминг** — `Booking` → `Meeting` (глоссарий запрещает «booking» для «Встречи»); черновики модели и эндпоинтов ниже исправлены на `Meeting` / `/api/meetings`
- **Модели** —
  - `EventType`: `name` required 1–100, `description` optional до 500 (отсутствует = пусто), `durationMinutes` 1–510, `slotStepMinutes` 1..`durationMinutes` (кросс-полевая проверка — серверная); в ответах вместе с `id`
  - `Slot`: `{ start, end, status: "free" | "occupied" }` — строковый enum; ответ эндпоинта слотов — голый массив слотов
  - `Meeting`: `eventTypeId`, `guestName` required 1–100, `start`, необязательный `topic` до 100 (пустая/пробельная нормализуется к отсутствию); `end` — только в ответе, вычисляется сервером
- **Время** — `offsetDateTime` во всех моделях (→ OpenAPI `date-time`, Java `OffsetDateTime`, TS `string`)
- **Ошибки** — единая модель `ProblemDetails` с `@error` (`type: "about:blank"`, `title`, `status`, `detail` на русском; массив `errors: [{ field, message }]` для `400`); `application/problem+json` для всех `400`/`404`/`409`
- **Теги** — `event-types`, `meetings`, `health`; русские описания через `@tagDoc`; openapi-generator режет контроллеры по тегам
- **Двойная генерация** —
  - коммитим только `docs/openapi.json` и `frontend/src/lib/api/schema.d.ts` — оба с дрейф-чеком в `mise run check`
  - Java: openapi-generator-maven-plugin на `generate-sources`, конфиг `backend/openapi-generator.yml` (generator `spring`, `interfaceOnly=true`, `useTags=true`, `dateLibrary=java8`, Jackson); `basePackage: io.github.abai45.backend` → интерфейсы контроллеров в `...backend.api`, DTO в `...backend.model`; сгенерированный код не коммитится
  - TS: openapi-typescript из `docs/openapi.json` → `frontend/src/lib/api/schema.d.ts`; openapi-fetch-обёртка пишется руками (`frontend/src/lib/api/client.ts`)

## Контрактная цепочка: генерация и дрейф-чек (тикет 1, #7)

- **Одна повторяемая задача генерации** — `mise run spec`: сначала `cd docs/spec/tsp && npm run generate` (`tsp compile .` по `tspconfig.yaml` пишет `docs/openapi.json`), затем `cd docs/spec/tsp && npm run generate:types` (`openapi-typescript ../openapi.json -o ../../frontend/src/lib/api/schema.d.ts`); порядок фиксирован — OpenAPI из TypeSpec, затем TS-типы из OpenAPI
- **Инструменты генерации** — пины живут в `docs/spec/tsp/package.json` (devDependencies `@typespec/compiler`, `@typespec/openapi3`, `openapi-typescript` одинаковой версии) вместе с lockfile; `npm install` в этой папке выполняет `mise run setup` — сборка в чистом состоянии работает без глобальных установок
- **Дрейф-чек** — `mise run spec-check`: прогоняет `mise run spec` и сверяет рабочее дерево командой `git status --porcelain -- docs/openapi.json frontend/src/lib/api/schema.d.ts` (ловит и изменённые, и новые незакоммиченные артефакты); входит в `mise run check` первым шагом — проверки только добавляются, не ослабляются
- **Коммитится** — `docs/spec/tsp/**` (включая `package-lock.json`), `docs/openapi.json`, `frontend/src/lib/api/schema.d.ts`. **Не коммитится** — сгенерированный Java-код (каталог `backend/target/` в `.gitignore`), `node_modules`
- **Серверная генерация** — `openapi-generator-maven-plugin` 7.26.0 на фазе `generate-sources`, ВСЕ параметры в `backend/pom.xml` (Maven-плагин не читает `configFile`, адрес артефактов — параметр `output`): generator `spring`, `interfaceOnly=true`, `skipDefaultInterface=true`, `useTags=true`, `useJakartaEe=true` (Spring Boot 4 → jakarta), `useSpringBoot3=true`, `useBeanValidation=false`, `openApiNullable=false` (плоский Jackson), `dateLibrary=java8` (`offsetDateTime` → `OffsetDateTime`); артефакты — `backend/target/generated-api` (не коммитится): интерфейсы `io.github.abai45.backend.api`, DTO `io.github.abai45.backend.model`; DTO генератора импортируют `io.swagger.v3.oas.annotations.media.Schema` (опции отключения у spring-генератора нет) — в pom добавлена зависимость `swagger-annotations-jakarta`; логика пишется вручную в корневом пакете `io.github.abai45.backend`
- **Валидация — ручная, сервер — источник истины (тикет 2, #8)** — `useBeanValidation=false`: аннотации генератора дают стандартные английские сообщения, а контракт требует `errors[]` с русскими текстами у полей; контроллер собирает все ошибки за проход (`EventTypeValidator`), бросает `ValidationException`, `ProblemDetailsAdvice` (`@RestControllerAdvice`) формирует `400 application/problem+json` (типы `about:blank`, `title`/`detail` по-русски); ограничение контракта на `slotStepMinutes ≤ durationMinutes` — тоже ручная проверка (в OpenAPI остаётся только `minValue: 1`)
- **Граница контракта по тикетам** — контракт растёт вместе с тикетами: тикет 1 (#7) добавляет модели `EventType`/`EventTypeView` и операцию `listEventTypes`; `errors.tsp` (RFC 9457 `ProblemDetails`) и остальные операции появятся со своими тикетами (#8 — `createEventType` и ответы `400`, #10 — `listSlots`, #11 — `createMeeting`, #13 — `listMeetings`), `healthCheck` впишется в контракт отдельным шагом
- **Модели списка типов** — `EventType` — тело создания (без `id`), `EventTypeView extends EventType` — ответ сервера с обязательным `id`; `GET /api/event-types` отвечает голым массивом `EventTypeView[]`; кросс-проверка `slotStepMinutes ≤ durationMinutes` — серверная, контракт фиксирует только `slotStepMinutes ≥ 1`
- **Клиент** — рукописная обёртка `frontend/src/lib/api/client.ts` поверх `openapi-fetch` с типом `paths` из `schema.d.ts`; страницы и компоненты не вызывают `fetch` напрямую

## Слоты записи и 404 (тикет 4, #10)

- **Расчёт слотов** — `SlotService` на сервере (источник истины, правила из «Параметров расписания»): окно 14 календарных дней со следующего дня, старты `09:30 + k × шаг` в `Asia/Almaty`, пока `старт + длительность ≤ 18:00`; длительность слота равна длительности типа; ответ — голый массив по возрастанию времени, `status: free` (занятость добавит #12)
- **Формат времени в ответах** — Jackson (Spring Boot 4) сериализует `OffsetDateTime` в UTC-форме (`...Z`); это валидный OpenAPI `date-time`, смещение владельца не теряется: фронтенд форматирует всё через `Intl` с явным `timeZone: Asia/Almaty` (канон #4), тесты проверяют границы в поясе владельца через `atZoneSameInstant`
- **404 в контракте** — `GET /api/event-types/{eventTypeId}/slots` отвечает `404 NotFoundResponse` (`application/problem+json`, `detail` «Тип встречи не найден.»); сервер бросает `NotFoundException`, `ProblemDetailsAdvice` формирует тело; `eventTypeId` — строковый id из `EventTypeView`
- **Мастер записи** — `BookingPage` (`/book`): шаги 1–4 в состоянии компонента (F5 → шаг 1, URL без параметров), степпер с возвратом по клику на пройденные шаги, выбор типа сбрасывает день/слот; шаг 2 — сетка месяца (←/→ по месяцам окна, дни вне окна и без свободных слотов некликабельны, счётчик «N св.»), список слотов дня «Свободно»/«Занято», подсветка выбора, «Продолжить» активна только после выбора слота; слоты перезапрашиваются при каждом входе на шаг; инфо-карточка шагов 2–4 (тип + бейдж длительности, описание, «Выбранная дата», «Выбранное время») — без имени владельца; шаги 3–4 реализует #11

## Занятость слотов в календаре (тикет 6, #12)

- **Статус считает сервер** — `SlotService.slotsFor` получает снапшот встреч (`MeetingStore.snapshot()`) и помечает `occupied` любой слот, строго пересекающийся с существующей встречей (**межтиповые пересечения тоже**; касание окончание=начало остаётся `free`); контракт из #10 не менялся — `Slot.status` уже описывал `free|occupied`
- **Гарантия свежести** — слоты отдаются по факту хранилища на момент запроса; фронт перезапрашивает шаг «Календарь» при каждом входе (ремонт mount), поэтому сразу после чужой записи день показывает реальную картину
- **UI** — занятый слот: «Занято», `disabled` + приглушение (`opacity-40 pointer-events-none`), выбрать нельзя → «Продолжить» не активируется (реализовано на шаге «Календарь» из #10, проверено поведением)
- **Окно на фронтенде — из ответа сервера** (замечание ревью): `CalendarStep` строит дни/месяцы окна из уникальных дней полученных слотов; клиентская арифметика «14 дней от сегодня» удалена — правила расписания на клиенте не дублируются
- **Изоляция тестов** — `MeetingsApiTest` помечен `@DirtiesContext(AFTER_CLASS)`: встречи не «протекают» в контекст `SlotsApiTest`, который проверяет «без записей все слоты свободны»

## Запись гостя: встречи, конфликт и атомарность (тикет 5, #11)

- **Контракт** — `Meeting` (`eventTypeId`, `guestName` 1–100, `start`, необязательный `topic` ≤100) и `MeetingView extends Meeting` (`end` — только в ответе); `POST /api/meetings`: `201 MeetingView`, `400`/`404`/`409` — `problem+json` (`ConflictResponse` добавлен в `errors.tsp`)
- **Правило пересечения** — серверный `MeetingStore.addIfNoOverlap`: строгое наложение интервалов запрещено между всеми встречами, **включая разные типы**; касание (окончание = начало) разрешено; проверка и добавление атомарны под монитором списка (in-memory, один процесс) — одновременные POST одного слота дают ровно один `201`, остальные `409`
- **`end` вычисляет сервер** — `start + durationMinutes` типа встречи; клиент `end` не отправляет (вне тела запроса по контракту)
- **Валидация записи** — `guestName` 1–100 вручную (`ValidationException` → `400 errors[]`), `topic` опционально ≤100 (иначе `400` c `field: "topic"`; пустая/пробельная тема нормализуется к отсутствию), неизвестный `eventTypeId` → `404` (`NotFoundException`), конфликт → `409` (`ConflictException`, `detail` на русском) — все через `ProblemDetailsAdvice`
- **Начало записи — только слот из окна** (замечание spec-оси ревью: сервер — источник истины правил расписания): `createMeeting` сверяет `start` с сеткой слотов типа (`SlotService.slotsFor`); чужое/прошлое/не-по-сетке время → `400 errors[]` по полю `start`; отсутствующие `eventTypeId`/`start` → `400`, а не 500; общая фабрика `FieldErrors`, общий предикат пересечения `IntervalOverlap` (используют `MeetingStore` и `SlotService`) и `EventTypeValidator.validateGuestName`/`validateTopic`/`normalizeTopic` — правило не дублируется
- **Мастер, шаги 3–4** — шаг «Имя»: поле «Ваше имя» (native `required`/`maxLength=100`) и сразу под ним необязательное «Тема разговора» (`maxLength=100`, подсказка «Необязательно, до 100 символов»); тело POST включает `topic` только при непустом (trim) значении; «Продолжить» через submit формы; шаг «Подтверждение»: сводка (тип+длительность, дата, время, имя — **тема не показывается**) + «Подтвердить запись» → pending «Записываю…»/`disabled`, единственный POST в мастере; исходы: `201` → `navigate('/book/success')`, `400` → тост с `detail`, сеть/5xx → тост «Не удалось записаться. Попробуйте ещё раз.» (кнопка активна), `409` → автовозврат на шаг «Календарь» (remount → перезапрос слотов), сброс выбранного слота, сообщение «Слот только что заняли, выберите другой» с `role="alert"` у карточки слотов, тип и имя сохранены
- **Экран «Вы записаны»** — `/book/success` без API-вызовов, данные через router state; строка «Тема: …» под именем гостя, только если `topic` из тела 201 непустой; прямой заход/F5 без состояния → `<Navigate to="/book">`; время — `Intl` в Asia/Almaty

## Предстоящие встречи владельца (тикет 7, #13)

- **Контракт** — `GET /api/meetings` отвечает голым массивом `MeetingView[]`; фильтр «ещё не начавшиеся» (`start >= now`) и сортировку по возрастанию `start` выполняет сервер (`MeetingStore.upcoming`) — UI не пересортировывает

- **Изоляция тестов** — `MeetingsApiTest` и `MeetingsListApiTest` помечены `@DirtiesContext(AFTER_CLASS)`: записанные встречи не «протека» в другие тестовые классы (SlotsApiTest ожидает пустое хранилище); прописанные встречи POST принимает, но в предстоящие не попадают

## Браузерный E2E с настоящим сервером (тикет 8, #14)

- **Инструмент** — Playwright (`@playwright/test`, chromium) в отдельном npm-проекте `e2e/`; конфигурация `e2e/playwright.config.ts` сама поднимает веб-серверы: бекенд `./mvnw spring-boot:run` (:8080, готовность по `GET /api/health`) и фронтенд `npm run dev` (:5173, vite-прокси `/api`) — `reuseExistingServer` вне CI
- **Без подмен** — сценарии идут только через UI и реальные HTTP-запросы настоящего сервера; конкурента в ветке 409 «записывает» тест через `request.post('/api/meetings')` — реальный API-запрос, не мок
- **Команды** — все сценарии одной командой `mise run e2e`; вход в общую проверку: `mise run check` вызывает `mise run e2e` последним шагом; браузер ставится в `mise run setup` (`npx playwright install chromium`) — CI получает его вместе с зависимостями
- **Сценарии (4)** — 1) владелец: форма → тип в списке + тост; 2) гость полный путь: тип → календарь (первый кликабельный день, первый свободный слот) → имя → сводка → «Вы записаны» → встреча видна владельцу в «Предстоящих» (запись **без темы** — регрессионный якорь, без правок селекторов); 3) 409: слот перехвачен реальным POST перед подтверждением → автовозврат на календарь, `role=alert` «Слот только что заняли, выберите другой», слот стал «Занято»/`disabled`, «Продолжить» неактивна; 4) тема разговора: поле на шаге «Имя» → «Вы записаны» с «Тема: …» → у владельца строка под именем гостя; запись без темы — строки темы нет (на успехе и в карточке)
- **Стабильные селекторы** — дни календаря несут `data-day` (yyyy-mm-dd пояса владельца); карточки отличаем от тостов Sonner (те тоже `listitem`) фильтром по строке метаданных
- **Изоляция данных** — имена с `Date.now()`, тесты последовательны (`workers: 1`); in-memory хранилище живёт один прогон — сценарии не должны зависеть по времени на уже занятые слоты (выбирается первый свободный)

## Структура пакетов бэкенда (issue #17, поверх решения #7)

- **Разнесение рукописного кода** — `io.github.abai45.backend`: `.controller` (HealthController, EventTypesController, MeetingsController, ProblemDetailsAdvice, NotFoundException, ConflictException), `.service` (SlotService), `.store` (EventTypeStore, MeetingStore), `.validation` (EventTypeValidator, FieldErrors, IntervalOverlap, ValidationException); `BackendApplication` остаётся в корне — component-scan покрывает подпакеты
- **Генерируемое не трогаем** — интерфейсы `.api` и DTO `.model` создаёт openapi-generator на сборке (не коммитятся, см. #7); рукописных `dto` не заводим, чтобы не плодить дубли контрактных моделей и слой мапперов без нужды
- **Направление зависимостей без циклов** — controller → service/store/validation; service → store/validation; store → validation; validation → только модели контракта; пакетные классы (исключения, фабрики, утилиты) становятся `public` для кросс-пакетных вызовов
- **Тесты не зависят от пакетов** — все API-тесты идут через HTTP-шов, рефакторинг не меняет ни одного теста

## Экран владельца `/owner` (вопрос карты #3, 31.10.2026)
- **Страница** — один `h1` «Владелец» + рядом ссылка «На главную» → `/`; секции с `h2`: «Создать тип встречи», «Типы встреч», «Предстоящие встречи»

Ручной ввод и нативные атрибуты сохраняются, сервер — источник истины
- **Отправка формы** — pending: кнопка «Создать тип встречи» → «Создаю…», `disabled`, повторный submit невозможен; успех `201`: сброс полей, `GET /api/event-types` (только типы — `GET /api/meetings` не перезапрашиваем, новый тип встреч не добавляет), тост «Тип встречи «X» создан»; сбой сети/`5xx`: тост «Не удалось создать тип встречи. Попробуйте ещё раз.», кнопка снова активна; дубли названий типов разрешены — проверки уникальности нет ни на клиенте, ни на сервере
- **Список типов** — read-only карточки: название жирно, описание muted (только если есть), строка метаданных «Длительность 30 мин · Шаг 15 мин»; порядок — как в ответе API; без действий (редактирование/удаление вне скоупа); `empty`: «Типов встреч пока нет» + «Создайте первый тип — гость сможет записаться на него.»
- **Список предстоящих встреч** — плоский список, по возрастанию `start` (как отдаёт API), без группировки по дням; карточка: название типа (join по `eventTypeId` с загруженным списком типов, fallback «Тип встречи» — реально не случится, удаления типов нет), «Гость: имя», время «27 октября, 10:00–11:00» — всегда Asia/Almaty через `Intl.DateTimeFormat` (`ru-RU`, часовой пояс задан явно); `empty`: «Предстоящих встреч пока нет» + «Здесь появятся встречи, на которые запишутся гости.»
- **Загрузка** — `GET /api/event-types` и `GET /api/meetings` параллельно при монтировании; у каждой секции своя четвёрка `loading/empty/error/ok` по канону #5; «Повторить» перезапрашивает только свою секцию; секции независимы
- **Сценарии в спеке (4)** — открытие `/owner` (параллельная загрузка обеих секций); создание типа — успех; создание типа — `400`; сбой сети/`5xx` у секции (упавшая секция в `error`, остальные живут дальше)
- **Поправка к базе компонентов (#5)** — добавлены `Textarea` и `Sonner` (тост — только для submit-исходов формы; тост ≠ глобальный оверлей, ошибки загрузки секций остаются инлайном); `Alert` исключён из базы — единственным назначением была форма

## Экран гостя `/book` (вопрос карты #4, 31.10.2026)

- **Страница** — мастер записи из 4 шагов с видимым прогрессом: тип → календарь → имя → подтверждение
- **Прогресс** — степпер с подписями «Тип», «Календарь», «Имя», «Подтверждение»; текущий шаг выделен; клик по пройденным шагам разрешён (возврат), «вперёд» — только кнопками; состояние мастера в памяти: F5 сбрасывает на шаг 1, URL всегда `/book` без параметров; смена типа на шаге 1 сбрасывает выбранный слот, имя не трогает
- **Шаг 1 «Тип»** — `GET /api/event-types` при монтировании; карточки кликабельны: клик по карточке = выбор типа и переход на шаг 2; вид карточек как в `/owner`: название жирно, описание muted (только если есть), «Длительность 30 мин · Шаг 15 мин»; состояния по канону #5; `empty` — «Типов встреч пока нет» + «Вернитесь позже: владелец ещё не добавил ни одного типа.» + кнопка «На главную» → `/`
- **Инфо-карточка** (шаги 2–4) — без блока хоста: владелец гостям не показывается, «Tota» на референсе — чужой макет; содержимое: название типа + бейдж «30 мин», описание (только если есть), блок «Выбранная дата» («вторник, 31 марта» или «День не выбран») и блок «Выбранное время» («10:00–11:00» или «Время не выбрано»); на шаге 1 карточки нет
- **Шаг 2 «Календарь»** — `GET /api/event-types/{eventTypeId}/slots`; сетка месяца: дни вне окна записи приглушены и некликабельны, стрелки ←/→ листают месяцы, пересекающие окно; под числом дня счётчик «N св.» — только если у дня ≥1 свободного слота; день без свободных слотов некликабельен и без счётчика
- **Выбор слота** — предвыбора нет; клик по дню → справа список всех слотов дня: «Свободно» (кликабельно) / «Занято» (приглушено, некликабельно); выбранный слот подсвечен, «Продолжить» активна только после выбора свободного слота; `empty` дня — «Свободных слотов на этот день нет»
- **Шаг 3 «Имя»** — поля: «Ваше имя» (`Input`, `label`, `required`, `maxLength=100`) и сразу под ним «Тема разговора» (`Input`, `label`, необязательное, `maxLength=100`, подсказка «Необязательно, до 100 символов»); продвижение — «Продолжить» с нативной клиентской проверкой (пустое имя не пропускается); тело запроса включает `topic` только при непустом (trim) значении; серверная валидация отложена до POST; «Назад» возвращает на календарь, имя и тема сохраняются
- **Шаг 4 «Подтверждение»** — сводка: название типа + длительность, «Выбранная дата», «Выбранное время», «Имя: …» (**тема на этом шаге не отображается**); кнопка «Подтвердить запись» → `POST /api/meetings` — единственная запись в мастере, шаги 1–3 без API-записи; pending — «Записываю…», `disabled`, повторный submit невозможен; исходы: `201` → экран «Вы записаны»; сбой сети/`5xx` → тост Sonner «Не удалось записаться. Попробуйте ещё раз.», кнопка снова активна; `400` (защитный случай — имя уже проверено на клиенте) → тост с `detail` из problem+json, мастер не двигается; «Назад» возвращает на имя, данные сохранены
- **`409`** — автовозврат на шаг 2 «Календарь»: слоты перезапрошены, выбранный слот сброшен, сообщение «Слот только что заняли, выберите другой» с `role="alert"` у списка слотов; тип и имя сохраняются — гость проходит «Имя → Подтверждение» заново с новым слотом
- **Свежесть слотов** — каждый вход на шаг 2 («Назад», клик по степперу, после 409) → повторный `GET .../slots` со скелетоном; кэш слотов — только внутри текущего показа шага
- **Экран «Вы записаны»** — отдельный маршрут `/book/success` без API-вызовов: `h1` «Вы записаны»; карточка: название типа, «Гость: имя», время «27 октября, 10:00–11:00» — всегда Asia/Almaty через `Intl.DateTimeFormat` (`ru-RU`, часовой пояс явно), как в `/owner`; кнопка «На главную» → `/`; прямой заход по ссылке или F5 без состояния мастера → редирект на `/book`
- **Раскладка** — по канону #5: мобилка — вертикальная последовательность (инфо-карточка → календарь → список слотов), десктоп (перелом `md`) — три колонки по референсу; «Назад» / «Продолжить» под списком слотов
- **Сценарии в спеке (6)** — открытие `/book` (загрузка типов); пустой список типов; выбор типа и слота (календарь + список слотов); запись — успех → «Вы записаны»; `409` на «Подтвердить запись» → возврат на календарь с перезагрузкой слотов; сбой сети/`5xx` на «Подтвердить запись» → тост

- **Стиль** — светлая тема shadcn (нейтральная, Geist), без переключателя тёмной темы; адаптивность через Tailwind-утилиты
- **Язык UI** — русский
- **Скоуп** — чисто фронтенд: бекенд и API не трогаем, моков нет

## Модель данных (черновик)

```
EventType   id, name, description, durationMinutes, slotStepMinutes
Meeting     id, eventTypeId, guestName, topic?, start, end
            end = start + durationMinutes, вычисляется на сервере
            topic опционален; пустая/пробельная тема нормализуется к отсутствию
```

## API-эндпоинты (черновик)

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/event-types` | создать тип встречи (владелец) |
| GET | `/api/event-types` | список типов встреч |
| GET | `/api/event-types/{eventTypeId}/slots` | слоты окна на 14 дней вперёд, статус `free` / `occupied` |
| POST | `/api/meetings` | записаться: `{ eventTypeId, guestName, start, topic? }` |
| GET | `/api/meetings` | предстоящие встречи владельца |
| GET | `/api/health` | дымовой эндпоинт, отвечает 200 |

Коды ошибок: `400` — невалидные параметры, `404` — неизвестный тип встречи,
`409` — слот занят или интервал пересекается с существующей бронью.
