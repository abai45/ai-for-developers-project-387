# REVIEW.md — критерии ревью «Календаря звонков»

Файл читается **независимым ревьюером** (автоторевью в GitHub и человеком). Ревьюер
не продолжает сессию реализации и не правит код: только замечания.

## Как формулировать замечание

Каждое замечание содержит: **файл, строку, условие ошибки и её последствие**.
«Красиво/некрасиво» — не замечание. Если подтверждённых дефектов нет — ревьюер
говорит об этом прямо. Форматирование проверяет линтер, повторять его вывод
в ревью не нужно.

## Инварианты календаря (проверять всегда)

1. **Занятый слот не остаётся доступным для повторной записи.** Перепроверка на
   сервере при бронировании, конфликт → `409` (RFC 9457 `problem+json`).
2. **Время — ISO-8601 с явным смещением владельца** (`2026-10-27T09:30:00+05:00`);
   сервер считает `end` из длительности типа встречи, клиенту конец не доверяется.
3. **Список встреч владельца — только предстоящие**, по возрастанию `start`.
4. **Скоуп операций не расширяется молча**: отмена брони, редактирование/удаление
   типов и встреч — вне скоупа (docs/decisions.md). PR, добавляющий эндпоинт
   за пределами скоупа, требует явного решения человека.
5. **Контрактная цепочка**: правка только в `docs/spec/tsp/` → `mise run spec`;
   `docs/openapi.json` и `frontend/src/lib/api/schema.d.ts` в diff, не изменённые
   генерацией, — сигнал ручной правки, это дефект.
6. **Ошибки — только `application/problem+json`** с `field` для ошибок валидации.

## Глубина проверки — по последствиям ошибки, не по строкам diff

| Изменение | Что проверять перед мержем |
| --- | --- |
| Подпись кнопки, текст UI | Соответствие тексту задачи (спеке) и отражение в интерфейсе |
| Расчёт доступных слотов | Основной сценарий, пересечения бронирований, соседние случаи |
| Валидация нового поля | Негативный сценарий спеки + нормализация пустых значений |
| Права GitHub Actions | Изменение доступа к коду и секретам — отдельное решение человека |

## Сценарии проверяемой доработки берутся из согласованной спеки

Для темы разговора (#5 → спека #10):

- **Основной**: гость указал тему → она в теле `201`, на экране «Вы записаны»
  и строкой под именем гостя в карточке предстоящей встречи владельца.
- **Негативный**: `topic` 101 символ → `400` с `field: "topic"`; пустая/пробельная
  тема нормализуется сервером к отсутствию; строка темы не рендерится без значения.
- **Соседний**: запись без темы работает как раньше; существующий e2e-сценарий
  проходит без правок селекторов (регрессионный якорь).

## Роль человека

Каждое замечание ревьюера человек разбирает сам: подтверждённую ошибку передаёт
автору командой `/oc` в PR; ошибочное замечание отклоняет с объяснением.
Решение о мерже фиксирует человек после зелёных проверок на текущем head SHA.
